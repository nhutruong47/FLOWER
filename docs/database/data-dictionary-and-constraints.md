## 1. Global Database Standards (`CLAUDE.md` §6, `ADR-0003`)

1. **Target Engine:** PostgreSQL 16 (`DEC-018`).
2. **Naming:** `snake_case` for all table, column, index, and constraint names; table names are plural (`branches`, `products`, `branch_inventories`, `orders`, `order_lines`).
3. **Primary Keys:** Every table has `id uuid PRIMARY KEY` (generated by the application as UUIDv7 or UUIDv4, or `gen_random_uuid()` default in SQL).
4. **Timestamps & Time Zones:** Every table has `created_at timestamptz NOT NULL DEFAULT now()` and `updated_at timestamptz NOT NULL DEFAULT now()`. All timestamps are stored and exchanged in **UTC** (`CLAUDE.md` §5, §6).
5. **Money:** All monetary columns (`unit_price`, `unit_price_snapshot`, `line_total_snapshot`, `items_subtotal`, `delivery_fee`, `discount_amount`, `total_amount`, `amount`, `refund_amount`) use **`numeric(19, 2) NOT NULL`** (never `real`, `double precision`, or `float`).
6. **Soft-Delete Policy (No Physical Deletion of Operational/Master Records):**
   - Master entities (`branches`, `staff_users`, `customers`, `product_categories`, `products`) are **never physically deleted** (`DELETE FROM` is prohibited in application code) because historical orders (`REQ-005`, `REQ-006`) and audit trails (`REQ-008`) reference them via foreign keys (`ON DELETE RESTRICT`). Instead, they use an explicit lifecycle `status` column (`ACTIVE` / `INACTIVE` / `DISABLED` / `ARCHIVED`).
   - Operational and ledger tables (`inventory_movements`, `order_status_history`, `payment_webhook_events`, `payment_refunds`, `audit_logs`) are **strictly append-only and immutable** (no `UPDATE` or `DELETE`).
7. **Normalization vs. Controlled Denormalization:**
   - The schema is in **Third Normal Form (3NF)** for all master and live operational data (`products`, `branch_product_prices`, `branch_inventories`).
   - **Controlled Denormalization for `REQ-006`:** `order_lines` intentionally denormalizes `sku_snapshot`, `product_name_snapshot`, `unit_price_snapshot`, and `line_total_snapshot` at order placement time so historical orders remain 100% immune to future catalog edits or branch price changes (`REQ-006`).

## 2. Complete Table & Constraint Specifications by Module

### 2.1 Module `shared` (`com.flowerchain.shared`)

#### Table 1: `idempotency_records`
- **Purpose:** Stores `Idempotency-Key` request hashes and responses for retryable mutations (placing orders, initiating payments, recording refunds — `CLAUDE.md` §7, `NFR-004`).
- **Columns:**
  - `id uuid PRIMARY KEY`
  - `idempotency_key varchar(128) NOT NULL`
  - `actor_scope varchar(128) NOT NULL` (authenticated user ID or IP/client hash)
  - `endpoint_pattern varchar(128) NOT NULL`
  - `request_hash varchar(64) NOT NULL` (SHA-256 of payload to reject key reuse with different payload)
  - `response_status integer NOT NULL`
  - `response_body jsonb NOT NULL`
  - `expires_at timestamptz NOT NULL`
  - `created_at timestamptz NOT NULL DEFAULT now()`
  - `updated_at timestamptz NOT NULL DEFAULT now()`
- **Unique Constraints:** `uq_idempotency_key_scope UNIQUE (idempotency_key, actor_scope, endpoint_pattern)`

  - `old_values jsonb NULL`
  - `new_values jsonb NULL`
  - `ip_address varchar(64) NULL`
  - `created_at timestamptz NOT NULL DEFAULT now()`
  - `updated_at timestamptz NOT NULL DEFAULT now()`

## 4. Concurrency, Stock Reservation, Overselling Prevention, and Idempotency Analysis

1. **Preventing Negative Stock & Overselling (`REQ-007`, `TEST-008`, `TEST-009`):**
   - **Deterministic Lock Ordering:** Before locking multiple products at a branch, the service sorts `productId` values ascending (`ORDER BY product_id ASC`) and executes:
     ```sql
     SELECT id, branch_id, product_id, available_stock, reserved_stock, version
     FROM branch_inventories
     WHERE branch_id = :branchId AND product_id IN (:sortedProductIds)
     ORDER BY product_id ASC
     FOR UPDATE;
     ```
   - **Two-Phase Stock State (`available_stock` & `reserved_stock`):**
     - **On Order Placement (`FR-017`, `FR-021`):** `available_stock = available_stock - qty`, `reserved_stock = reserved_stock + qty`. Writes `inventory_movements` row (`reason_code = 'ORDER_RESERVED'`, `quantity_delta = -qty`). Because `available_stock` is immediately decremented under the row lock, a second concurrent customer cannot claim those units (`REQ-007`).
     - **On Verified Payment Webhook (`FR-026`):** `reserved_stock = reserved_stock - qty` (`available_stock` was already decremented). Writes `inventory_movements` row (`reason_code = 'ORDER_CONFIRMED'`).
     - **On Cancellation / Payment Timeout (`FR-017`, `FR-024`):** `available_stock = available_stock + qty`, `reserved_stock = reserved_stock - qty`. Writes `inventory_movements` row (`reason_code = 'ORDER_RELEASED'`, `quantity_delta = +qty`).
   - **Database Defense-in-Depth:** `CHECK (available_stock >= 0)` and `CHECK (reserved_stock >= 0)` guarantee that even a bug in application code cannot commit negative stock (`TEST-009`).
2. **Preventing Duplicate Payments & Duplicate Orders (`REQ-010`, `TEST-012`):**
   - **Webhook Deduplication (`payment_webhook_events`):** When a verified webhook arrives (`REQ-009`), the service inserts into `payment_webhook_events (provider, provider_event_id, ...)`. If two threads deliver the exact same webhook concurrently, PostgreSQL's `uq_payment_webhook_provider_event_id UNIQUE (provider, provider_event_id)` allows only one transaction to succeed and blocks the duplicate (`REQ-010`).
   - **Client Retry Deduplication (`idempotency_records`):** `POST /api/v1/storefront/orders` and `POST /api/v1/admin/payments/{id}/refunds` require an `Idempotency-Key` header enforced by `uq_idempotency_key_scope`.
